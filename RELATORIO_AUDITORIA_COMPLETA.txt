1. VISÃO GERAL DO PROJETO
================================================================================

O Zenith Ride é um aplicativo de ride-sharing (tipo Uber) voltado para Angola
(moeda Kz, foco em Luanda). Stack tecnológica:

  Frontend:  React 18 + TypeScript + Vite + TailwindCSS + Capacitor (mobile)
  Backend:   Supabase (PostgreSQL + Auth + Storage + Realtime + Edge Functions)
  Mapas:     Mapbox GL JS + H3 (geospatial)
  AI:        Google Gemini (chat Kaze) + ElevenLabs (voz) + Sentinel Vision
  Voice:     Web Speech API + Python TTS Server + ElevenLabs
  Testes:    Playwright (E2E mínimo)
  Deploy:    Vercel

Estrutura de pastas principal:
  zenith-ride-build/
  ├── src/
  │   ├── components/     (~40+ componentes React)
  │   ├── contexts/       (AuthContext)
  │   ├── hooks/          (6 hooks customizados)
  │   ├── lib/            (~15 utilitários)
  │   ├── services/       (~10 serviços)
  │   ├── store/          (Zustand store)
  │   ├── config/         (env.ts)
  │   └── types.ts        (definições de tipos)
  ├── supabase/           (Edge Functions + 53 migrations)
  ├── e2e/                (2 testes smoke mínimos)
  └── zenith_schema_final.sql  (schema completo ~800 linhas)

--- 3.1. src/contexts/AuthContext.tsx (795 linhas) ---

O que faz: Provider central de autenticação. Gerencia sessão Supabase,
carregamento de dados do usuário, Google OAuth, login/logout, verificação
de suspensão de conta, e auto-repair quando o trigger do banco falha.

BUG CRÍTICO — Import logError não existe:
  Arquivo: src/contexts/AuthContext.tsx:23
  Código:
    import { logError } from '../lib/logger';

  O arquivo src/lib/logger.ts só exporta um objeto 'logger':
    // src/lib/logger.ts (7 linhas):
    const isDev = import.meta.env.DEV;
    export const logger = {
      warn: (...args: unknown[]) => { if (isDev) console.warn(...args); },
      info: (...args: unknown[]) => { if (isDev) console.info(...args); },
      error: (...args: unknown[]) => { console.error(...args); },
    };

  NÃO EXISTE exportação 'logError'. Isso é usado nas linhas 363, 389 e 519.
  Quando o auto-repair falhar (cenário de erro), o próprio handler de erro
  vai CRASHAR — "logError is not a function".

  Impacto: O sistema de error-reporting falha EXATAMENTE quando mais precisa.
  Severidade: 🔴 CRÍTICO

Race condition no autoRepairInProgress:
  Arquivo: src/contexts/AuthContext.tsx:366-393
  Código simplificado:
    const autoRepairInProgress = { current: false };

    async function ensureUserExists() {
      if (autoRepairInProgress.current) return;
      autoRepairInProgress.current = true;
      try {
        // ... repair logic com timeout de 30s (linha 369-372)
        // Se timeout dispara, autoRepairInProgress = false
        await supabase.rpc('ensure_user_exists', ...);
      } finally {
        autoRepairInProgress.current = false; // pode ser tarde demais
      }
    }

  O timeout de 30s reseta o flag para false, mas o try ainda pode estar
  rodando. Dois requests concorrentes podem ambos entrar no repair.

  Impacto: Race condition rara mas possível.
  Severidade: 🟡 MÉDIA

Role intent controllável pelo cliente:
  Arquivo: src/contexts/AuthContext.tsx:125-141
  Código:
    function persistStoredRoleIntent(role: UserRole) {
      if (role === UserRole.PASSENGER || role === UserRole.DRIVER ||
          role === UserRole.FLEET_OWNER) {
        localStorage.setItem('auth_role_intent', role);
      }
    }

  Um passageiro pode setar 'auth_role_intent' = 'fleet_owner' no localStorage.
  Isso faz o sistema chamar supabase.rpc('set_my_role_fleet_owner').
  Se o RPC não validar server-side, é ESCALAÇÃO DE PRIVILÉGIOS.

  Impacto: Possível escalação (depende do RLS no banco).
  Severidade: 🟠 ALTA

resolveSessionRole não memoizado:
  Arquivo: src/contexts/AuthContext.tsx:716
  Código:
    const role = resolveSessionRole((safeDbUser as any)?.role);
    // resolveSessionRole lê localStorage a cada render

  Isso roda em CADA render de CADA componente que consome o contexto.
  Poderia ser useMemo.

  Severidade: 🟡 MÉDIA (performance)

--- 3.4. .env — SEGURANÇA CRÍTICA ---

  ⚠️  API KEYS SECRETAS EXPOSTAS NO BUNDLE DO CLIENTE:

  Linha 15: VITE_GEMINI_API_KEY=AIzaSyC9c...

    → Qualquer pessoa pode extrair do bundle e usar

  Linha 17: VITE_ELEVENLABS_API_KEY=sk_79dd...

    → Prefixo VITE_ = EXPOSTO ao cliente
    → Qualquer pessoa pode gerar áudio usando sua conta

  Linha 20: RESEND_API_KEY=re_jQ4G...
    → Sem prefixo VITE_ = não exposto no bundle
    → Mas ainda está no .env que pode vazar

  Código no .env:
    VITE_GEMINI_API_KEY=AIzaSyC9c...
    VITE_ELEVENLABS_API_KEY=sk_79dd...
    RESEND_API_KEY=re_jQ4G...

  O .env.example diz que GEMINI_API_KEY "goes to Edge Function secret",
  mas o .env real usa VITE_ prefix, contradizendo a documentação.

  Impacto: Perda financeira direta, uso indevido de APIs
  Severidade: 🔴 CRÍTICO

    Isso roda quando o módulo é importado. Nunca é limpo.
    Em SSR, testing com jsdom, ou HMR, vaza memória.

  BUG — Race condition no _updateKmPerk:
    Arquivo: src/services/rideService.ts:754-769
    Código:
      async _updateKmPerk(userId: string, km: number) {
        const { data } = await supabase.from('profiles')
          .select('km_total').eq('user_id', userId).single();
        const newTotal = (data?.km_total ?? 0) + km;
        await supabase.from('profiles')
          .update({ km_total: newTotal }).eq('user_id', userId);
      }

    Read-modify-write clássico. Duas corridas rápidas sobrescrevem.
    Deveria ser um RPC atômico no banco.

  ISSUE — updateRideStatus não usa RPC atômico:
    Enquanto acceptRide usa 'accept_ride_atomic' e cancelRide usa
    'cancel_ride_safe', o updateRideStatus faz update direto.
    Pode ter race conditions com updates concorrentes.

  AVALIAÇÃO: ✅ PRODUCTION-READY com ressalvas.
  Os RPCs atômicos para accept/decline/cancel são sólidos.
