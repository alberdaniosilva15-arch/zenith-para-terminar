📋 DECOMPOSIÇÃO DAS FALHAS (o que a migration corrige)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FALHA 1: SELECT rides sem restrição
────────────────────────────────────
Antes:  anon + qualquer JWT lê todas as colunas de qualquer ride
Depois: anon → ZERO linhas
        passageiro → SÓ rides onde passenger_id = auth.uid()
        motorista → SÓ rides onde driver_id = auth.uid()
        searching → via RPC get_searching_rides() (dados mínimos)
SQL: policy rides_select_own_passenger + rides_select_own_driver
     + RPC get_searching_rides() retorna SÓ campos não-sensíveis

FALHA 2: DELETE driver_locations alheia
────────────────────────────────────────
Antes:  motorista autenticado APAGA registo de localização de QUALQUER motorista
Depois: motorista DELETE → SÓ driver_id = auth.uid()
        motorista UPDATE → SÓ driver_id = auth.uid()
        admin DELETE → SÓ com WITH CHECK
SQL: policy dl_delete_own_driver (USING driver_id = auth.uid())
     + policy dl_update_own_driver (WITH CHECK driver_id = auth.uid())

FALHA 3: UPDATE rides colunas sensíveis
────────────────────────────────────────
Antes:  passageiro pode PATCH própria ride e alterar price_kz, origin_lat,
        dest_address, etc. mesmo que o WITH CHECK só verifique status='cancelled'
Depois: UPDATE directo BLOQUEADO → só via RPC
        cancel_ride() → SÓ altera status, cancelled_at, cancel_reason
        accept_ride() → SÓ altera driver_id, status, accepted_at, driver_confirmed
SQL: cancel_ride(UUID,TEXT) + accept_ride(UUID) — sem policy de UPDATE geral

FALHA 4: GPS exacto em driver_locations para toda a gente
───────────────────────────────────────────────────────────
Antes:   anon + qualquer JWT lê location (WKB Point com lat/lng exacto)
Depois:  get_available_drivers() → SÓ h3_index_res9 (~150m resolução)
         get_tracking_driver_location(UUID) → GPS exacto SÓ durante ride activa
         driver SELECT própria → SÓ driver_id = auth.uid()
SQL: RPCs com verificação de role + ownership

FALHA 5: Cancelamento também altera campos não-relacionados
─────────────────────────────────────────────────────────────
Antes:  UPDATE rides SET status='cancelled', price_kz=0, origin_lat=...
        O passageiro pode alterar o que quiser junto com o cancelamento
Depois: RPC cancel_ride() SÓ altera status, cancelled_at, cancel_reason
        Colunas monetárias (price_kz) e geo (origin_lat) NÃO são tocadas
SQL: cancel_ride() — SET campos fixos, sem variáveis do caller
