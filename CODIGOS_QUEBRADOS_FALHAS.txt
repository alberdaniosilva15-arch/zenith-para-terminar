[FALHA 1] — CRÍTICA: RLS Policy abre TODAS as corridas a TODOS os utilizadores
════════════════════════════════════════════════════════════════════════════════

FICHEIRO: FIX_RLS_DEFINITIVO.sql (linhas 24-28)
SEVERIDADE: CRÍTICA — qualquer passageiro vê corridas de outros passageiros

--- CÓDIGO ATUAL (QUEBRADO) ---

  -- 2. Limpar a restrição de rides RLS (já corrigi no anterior, forçando tudo limpo agora):
  DROP POLICY IF EXISTS "rides: motorista vê" ON public.rides;
  CREATE POLICY "rides: motorista vê TODAS no mapa"
  ON public.rides FOR SELECT
  USING (true); -- Permitimos ver tudo se for Select. Lógica da UI já filtra.

--- EXPLICAÇÃO DO PROBLEMA ---

  USING (true) na política SELECT significa que QUALQUER utilizador autenticado
  (incluindo passageiros comuns) pode fazer SELECT em TODAS as linhas da tabela
  rides. Isto expõe:
    - Endereços de origem e destino de TODOS os passageiros
    - Nomes e IDs de passageiros
    - Preços pagos por outros passageiros
    - Dados de localização GPS em tempo real

  O comentário "Lógica da UI já filtra" está ERRADO — o Supabase aplica RLS
  ANTES de chegar ao frontend. Mas um atacante pode fazer query direta à API
  do Supabase (bypassing o frontend) e ver tudo.

  Este ficheiro SOBRESCREVEU as políticas corrigidas que existiam na migration
  20260422_fix_rides_rls_final.sql.

--- CÓDIGO CORRIGIDO SUGERIDO ---

  -- REMOVER este ficheiro completamente e restaurar as policies da migration original:

  -- Passageiro vê as suas próprias corridas
  CREATE POLICY "rides: passageiro vê as suas corridas"
    ON public.rides FOR SELECT TO authenticated
    USING (passenger_id = auth.uid());

  -- Motorista vê as corridas atribuídas
  CREATE POLICY "rides: motorista vê as suas corridas atribuídas"
    ON public.rides FOR SELECT TO authenticated
    USING (driver_id = auth.uid());

  -- Motoristas vêem corridas disponíveis (searching, sem motorista)
  CREATE POLICY "rides: motoristas vêem corridas disponíveis"
    ON public.rides FOR SELECT TO authenticated
    USING (status = 'searching' AND driver_id IS NULL);

[FALHA 2] — CRÍTICA: driver_locations com USING (true) no SELECT
════════════════════════════════════════════════════════════════════════════════

FICHEIRO: FIX_RLS_DEFINITIVO.sql (linhas 12-16)
SEVERIDADE: CRÍTICA — qualquer utilizador lê localização de qualquer motorista

--- CÓDIGO ATUAL (QUEBRADO) ---

  -- 1. Nova política ÚNICA de insert/update blindada:
  CREATE POLICY "driver_manage_own_location"
  ON public.driver_locations FOR ALL
  USING (true)
  WITH CHECK (auth.uid() = driver_id);

--- EXPLICAÇÃO DO PROBLEMA ---

  FOR ALL + USING (true) significa:
    - SELECT: qualquer utilizador vê TODAS as localizações de TODOS os motoristas
      (incluindo motoristas offline, que não estão disponíveis)
    - UPDATE: qualquer utilizador pode tentar update (mas WITH CHECK restringe)
    - DELETE: qualquer utilizador pode tentar delete (mas WITH CHECK restringe)

  O problema é o SELECT — motoristas que estão offline ou em corrida privada
  ainda têm a sua localização exposta a qualquer pessoa.

--- CÓDIGO CORRIGIDO SUGERIDO ---

  -- Políticas separadas para cada operação:

  -- Motorista vê e gere a sua própria localização
  CREATE POLICY "driver_manage_own_location"
  ON public.driver_locations FOR ALL
  USING (auth.uid() = driver_id)
  WITH CHECK (auth.uid() = driver_id);

  -- Público vê APENAS motoristas disponíveis (para o mapa)
  CREATE POLICY "driver_locations_public_read"
  ON public.driver_locations FOR SELECT
  USING (status = 'available');

[FALHA 6] — MÉDIA: KAZE_ALLOW_INSECURE_TLS=1 desliga verificação TLS
════════════════════════════════════════════════════════════════════════════════

FICHEIRO: .env (linha 23)
SEVERIDADE: MÉDIA — vulnerável a ataques Man-in-the-Middle

--- CÓDIGO ATUAL (QUEBRADO) ---

  # Kaze Agent — permitir TLS flexível (necessário em Angola com certificados instáveis)
  KAZE_ALLOW_INSECURE_TLS=1

--- EXPLICAÇÃO DO PROBLEMA ---

  Este flag desliga a verificação de certificados TLS no Kaze Agent (Python).
  Isto permite que um atacante faça Man-in-the-Middle (MITM):
    1. Atacante intercepta tráfego entre o app e o servidor
    2. Apresenta um certificado falso
    3. O Kaze Agent aceita porque TLS verification está desligada
    4. Atacante vê todas as mensagens, API keys, dados de utilizadores

  Em Angola, onde existem restrições de internet, MITM é uma ameaça real.

--- CÓDIGO CORRIGIDO SUGERIDO ---

  # Remover completamente:
  # KAZE_ALLOW_INSECURE_TLS=1

  # Se precisar de TLS flexível temporariamente, usar:
  KAZE_ALLOW_INSECURE_TLS=0

  # Ou configurar o certificado CA correto:
  # KAZE_CA_BUNDLE=/path/to/correct-ca-cert.pem

[FALHA 7] — MÉDIA: ensure_user_exists chamável por qualquer utilizador
════════════════════════════════════════════════════════════════════════════════

FICHEIRO: supabase/migrations/20260420_critical_fixes.sql (linhas 104-138)
SEVERIDADE: MÉDIA — qualquer utilizador pode criar registos de outros utilizadores

--- CÓDIGO ATUAL (QUEBRADO) ---

  CREATE OR REPLACE FUNCTION public.ensure_user_exists(
    p_user_id UUID,
    p_email   TEXT,
    p_name    TEXT DEFAULT '',
    p_role    TEXT DEFAULT 'passenger'
  )
  RETURNS void
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = public
  AS $$
  BEGIN
    -- 1. Garantir utilizador na tabela users
    INSERT INTO public.users (id, email, role)
    VALUES (p_user_id, p_email, p_role::user_role)
    ON CONFLICT (id) DO NOTHING;

    -- 2. Garantir perfil
    INSERT INTO public.profiles (user_id, name)
    VALUES (p_user_id, COALESCE(NULLIF(p_name, ''), split_part(p_email, '@', 1)))
    ON CONFLICT (user_id) DO NOTHING;

    -- 3. Garantir carteira
    INSERT INTO public.wallets (user_id, balance)
    VALUES (p_user_id, 0.00)
    ON CONFLICT (user_id) DO NOTHING;

    -- 4. Garantir privacidade VoIP
    INSERT INTO public.user_privacy (user_id)
    VALUES (p_user_id)
    ON CONFLICT (user_id) DO NOTHING;
  END;
  $$;

  GRANT EXECUTE ON FUNCTION public.ensure_user_exists(UUID, TEXT, TEXT, TEXT) TO authenticated;

--- EXPLICAÇÃO DO PROBLEMA ---

  SECURITY DEFINER + GRANT TO authenticated = qualquer utilizador autenticado
  pode chamar esta função com QUALQUER UUID e email.

  Cenário de ataque:
    1. Atacante sabe o UUID de outro utilizador (facilmente obtível)
    2. Chama: SELECT ensure_user_exists('uuid-vitima', 'attacker@email.com', 'Attacker', 'admin')
    3. Se o utilizador NÃO existe, cria-o com role 'admin'
    4. Se o utilizador JÁ existe, ON CONFLICT DO NOTHING impede (mas o atacante
       pode tentar com outro UUID)

  O factor de mitigação é que o Supabase Auth já cria o utilizador via trigger
  handle_new_user, então ON CONFLICT DO NOTHING protege na maioria dos casos.
  Mas se o trigger falhar, a porta fica aberta.

--- CÓDIGO CORRIGIDO SUGERIDO ---

  CREATE OR REPLACE FUNCTION public.ensure_user_exists(
    p_user_id UUID,
    p_email   TEXT,
    p_name    TEXT DEFAULT '',
    p_role    TEXT DEFAULT 'passenger'
  )
  RETURNS void
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = public
  AS $$
  BEGIN
    -- VALIDAÇÃO: só permite criar o próprio perfil
    IF p_user_id != auth.uid() THEN
      RAISE EXCEPTION 'Não podes criar perfil para outro utilizador.';
    END IF;

    -- VALIDAÇÃO: role só pode ser passenger, driver ou fleet_owner
    IF p_role NOT IN ('passenger', 'driver', 'fleet_owner') THEN
      RAISE EXCEPTION 'Role inválido: %', p_role;
    END IF;

    -- ... resto do código igual ...
  END;
  $$;

  -- Manter GRANT TO authenticated (necessário para auto-repair)

[FALHA 9] — MÉDIA: validate_tracking_token exposto a utilizadores anónimos
════════════════════════════════════════════════════════════════════════════════

FICHEIRO: supabase/migrations/20260425_add_ride_tracking_shares.sql (linha 123)
SEVERIDADE: MÉDIA — utilizadores não autenticados podem aceder a dados de tracking

--- CÓDIGO ATUAL (QUEBRADO) ---

  GRANT EXECUTE ON FUNCTION public.validate_tracking_token(UUID) TO anon, authenticated;

--- EXPLICAÇÃO DO PROBLEMA ---

  Esta função é concedida ao role "anon" (utilizadores NÃO autenticados).
  É intencional para links públicos de tracking (pais a monitorizar filhos).

  MAS: a função retorna coordenadas GPS do motorista em tempo real.
  Qualquer pessoa com o UUID de um token pode aceder à localização do motorista,
  mesmo que não seja o pai/responsável.

  Se um atacante descobrir UUIDs de tokens (ex: via URL partilhada),
  pode rastrear motoristas indefinidamente.

--- CÓDIGO CORRIGIDO SUGERIDO ---

  -- Opção 1: Limitar a informação retornada
  CREATE OR REPLACE FUNCTION public.validate_tracking_token(p_token UUID)
  RETURNS TABLE (ride_status TEXT, origin_address TEXT, dest_address TEXT)
  SECURITY DEFINER
  AS $$
  BEGIN
    -- NÃO retornar coordenadas GPS para anon
    RETURN QUERY
    SELECT r.status::TEXT, r.origin_address, r.dest_address
    FROM ride_tracking_shares rts
    JOIN rides r ON r.id = rts.ride_id
    WHERE rts.tracking_token = p_token
      AND rts.expires_at > now();
  END;
  $$;

  -- Opção 2: Criar função separada para GPS (só para authenticated)
  GRANT EXECUTE ON FUNCTION public.validate_tracking_token(UUID) TO authenticated;
